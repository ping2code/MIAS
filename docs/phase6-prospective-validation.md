# Phase 6 — evidence maintenance and prospective validation

Phase 6 turns the Phase 4/5 research into a **forward-only, preregistered** test:

- Two hypotheses (H1′, H2′; see `phase6-preregistered-hypotheses.md`) are frozen and hashed before collection starts.
- Daily collection appends per-session evidence to an append-only ledger.
- Evaluation stays locked until a date gate and a sample gate are both met.

Nothing here tunes thresholds or changes production technical semantics, and nothing adds options analytics, signal
fusion or trading logic.

## Components

| Component | Role |
|---|---|
| `evidence/registry.py` | frozen H1′/H2′ and protocol, with SHA-256 hashes (`REGISTRY_HASH` is stored in every ledger row) |
| `evidence/pin.py` | resolves and validates the start pin (`evidence/prospective_start.json`); `python -m evidence.pin --commit <sha>` |
| `migrations/versions/0007_technical_evidence_ledger.py` | the `technical_evidence_ledger` table: append-only triggers, partial unique indexes; downgrade refused when rows exist |
| `persistence/technical_evidence_ledger.py` | insert-only repository: `inserted` / `duplicate` / `conflict`, and terminal failure rows |
| `persistence/technical_evidence_tools.py` | `reconcile` (missing sessions and identities) and `audit` (hash recomputation, registry/engine, snapshot references, triggers) |
| `evidence/collector.py` + `technical.runner` | daily collection behind `TECHNICAL_EVIDENCE_LEDGER_ENABLED` (default **false**); `--evidence-check` writes nothing |
| `evidence/plan.py` | dry run: universe, hashes, start candidate, request budget; **no network** |
| `evaluation/prospective_status.py` | no-peek status: coverage and gate progress only |
| `evaluation/prospective_validate.py` | the gated evaluation of H1′/H2′ (locked by default) |

The live runner and `evidence.*` never import `evaluation`; a subprocess test enforces this.

## Ledger (migration 0007)

The ledger records collection, provenance and integrity only. It never holds bars, prices, states, returns, vendor
payloads or keys.

- **Identity:** `(market_session_date, symbol, interval, engine_version, registry_hash)`. A partial unique index allows
  at most one `collected` row per identity.
- **`evidence_hash`:** SHA-256 over the material fields:
  - format version and identity;
  - provider, adjusted, delay, extended hours;
  - `bar_count` and `bar_content_hash`;
  - the snapshot reference.

  `code_commit`, the timestamps and `backfilled` are **not** included. So an identical retry from newer code is a
  *duplicate* that keeps the original row's provenance.
- **Conflicts:** different content for an accepted identity appends one `conflict` row per distinct hash, referencing
  the original. The original is never replaced.
- **Failures:** one `failed` row per *terminal* collection attempt, after the HTTP client's normal retries. Internal
  retries are not recorded. A later success is an ordinary `collected` row.
- **Append-only:**
  - there is no update or delete API;
  - PostgreSQL triggers reject UPDATE, DELETE and TRUNCATE;
  - SQLite triggers reject UPDATE and DELETE;
  - downgrade raises whenever the table has rows, and there is deliberately no override.
- **Snapshot reference (soft, no foreign key):** set only for the latest collected session, from the runner's
  snapshot. The warm-up is anchored to the reference day, so the reference is deterministic for that day. Sessions
  already accepted are never re-submitted, so the reference cannot turn a later run into a spurious conflict. The
  `audit` command verifies that the referenced `technical_snapshots` row exists and has the same content hash. For
  this reason the ledger requires `TECHNICAL_SNAPSHOT_PERSISTENCE_SHADOW_ENABLED=true`.

## Start pin (resolving the self-reference)

A commit cannot contain its own hash. So:

1. The registry freezes the *rule*.
2. The Phase 6 freeze commit is merged to main.
3. A follow-up commit adds `evidence/prospective_start.json`, generated by `python -m evidence.pin --commit <freeze
   sha>`. It records:
   - `prospective_freeze_commit`, `freeze_commit_time`;
   - `prospective_start_session`, `earliest_evaluation_session`;
   - `registry_hash`.

`validate_pin` recomputes every derived field from the calendar and the frozen registry. The collector, `status`,
`reconcile`, `audit` and `validate` all refuse to run without a valid pin (exit 2). Only `--evidence-check` and the dry
run work unpinned.

## Daily collection

It is disabled by default: the scheduler registration of `technical` stays `enabled=False`, and so does the ledger
flag. To operate it, the operator starts the scheduler at about **08:00 America/New_York** with:

```
TECHNICAL_SCHEDULE_ENABLED=true
TECHNICAL_INTERVAL_SECONDS=86400
TECHNICAL_TIMEOUT_SECONDS=1800
TECHNICAL_EVIDENCE_LEDGER_ENABLED=true
TECHNICAL_SNAPSHOT_PERSISTENCE_SHADOW_ENABLED=true
DATABASE_URL=...            # the MIAS database, migrated to 0007
MARKET_DATA_PROVIDER=polygon, MARKET_DATA_API_KEY=... (process environment only; never .env)
```

- With the ledger enabled and no `--symbols` argument, the runner uses the frozen universe (8 symbols).
- The time of day is a soft target. Each run records every eligible, not-yet-accepted session in its window, so drift
  or a missed day is backfilled naturally:
  - 5m: 10 sessions;
  - 1h: 90;
  - 1d: 450.

  Rows collected after the expected collection date (the next trading day) are labelled `backfilled=true`.
- Beyond the 5m window, a missed 5m session cannot be recovered by the runner, and `reconcile` reports it as missing.
- **Budget (dry run):** per symbol, one 5m fetch (1 page) and one 30m fetch (≤ 9 pages, counted in base minute
  aggregates). That is ≤ 80 requests per day, about 16 minutes at 12 s pacing.

The runner fails closed (exit 2, before any network call) when any of these holds:

- no valid pin;
- shadow persistence off;
- an engine version other than `phase4c-v2`;
- a symbol outside the universe;
- the git commit is unavailable;
- the database is not configured.

Ledger database failures exit 1 and never change the technical output. Conflicts or failure rows also make the run
exit 1, so the scheduler surfaces them.

## Operational validation (pre-cutoff; not evidence)

```
python -m evidence.plan                          # no network: universe, hashes, start candidate, request budget
python -m technical.runner --evidence-check      # needs the market-data key; writes nothing
```

`--evidence-check` fetches the normal runner windows for the 8 symbols and reports, per symbol × interval:

- sessions checked;
- complete sessions;
- incomplete sessions, with their bar counts;
- the snapshot-reference session.

It reports no prices, states or returns. Without a pin, every session in the window is pre-cutoff: **operational
validation only, never evidence**.

## Monitoring (no-peek)

```
python -m evaluation.prospective_status              # coverage + gate progress; no statistics
python -m persistence.technical_evidence_tools reconcile
python -m persistence.technical_evidence_tools audit # exit 1 on any integrity problem
```

## Evaluation gate

`python -m evaluation.prospective_validate` stays locked (exit 3) until **both** of these hold:

- today ≥ `earliest_evaluation_session`;
- there are ≥ 120 complete sessions.

While locked it fetches nothing, computes no state or statistic, and prints:

```
Evaluation locked. Earliest evaluation date: YYYY-MM-DD. Eligible sessions: N / 120. No hypothesis statistics were computed.
```

`--early-look-override` runs anyway. Every output field and each hypothesis is then labelled
`NON_PREREGISTERED_EARLY_LOOK`, and must never be reported as a preregistered result.

After the gate opens:

- bars are re-fetched and each session's hash is checked against the ledger; mismatches are excluded and listed;
- only H1′ and H2′ are computed, exactly as frozen;
- the result carries full provenance: label, format version, registry, protocol and hypothesis hashes, pin, code
  commit, evaluated window, excluded sessions, seed.

## Stop conditions (kept in force)

Collection or evaluation must stop, and the problem be escalated, if any of these holds:

- a production semantic or threshold would change;
- the scheduler would have to be auto-enabled;
- idempotency, or the separation of history from prospective data, fails;
- no-peek cannot be enforced;
- hashes could change after collection starts;
- raw data persistence becomes necessary;
- options or fusion logic enters scope.
